SECTION 01

Problem Statement & Current State Analysis

Current State

The enterprise data platform operates at significant scale, managing 30,000+ tables (mix of Iceberg and non-Iceberg formats) distributed across a four-layer architecture (Staging → Datalake → Base → Master). Data pipelines span multiple business domains — ERS, Finance, Financials, Membership, Claims, Travel, and more — each containing dozens to hundreds of tables per domain. Processing is orchestrated via Control-M with a one-to-one mapping between jobs and scripts. The platform currently has no dedicated, unified housekeeping strategy for Iceberg table maintenance at this scale.

A compounding problem exists in non-production environments. Dev, test, and preprod accounts mirror the production table structure but operate with no lifecycle controls — tables created for sprints, load tests, or experiments are never cleaned up. There is no registry of non-prod tables, no tracking of when they were created or last used, and no automated mechanism to reclaim storage. CloudTrail and Athena query logs show large numbers of non-prod tables with zero query activity for 60+ days, yet they continue to accumulate S3 storage and Glue catalog entries. This creates a secondary cost problem and governance risk entirely separate from the production housekeeping gap.

Key Problems

⚠️

No Stream-Level Identification

No logical grouping to determine which tables belong to which data flow or when they are safe to maintain.

🔄

AWS Auto-Optimization Interference

AWS's native optimization runs unpredictably, interfering with batch windows and competing for resources during SLA-critical runs.

📊

No Retention Control

No control over snapshot retention, orphan deletion, or compaction strategies. Leads to exponential metadata growth.

🔍

Zero Monitoring

No visibility into snapshot counts, orphan files, or small file proliferation. No inventory of which tables are even Iceberg.

🏗️

No Governance or Inventory

No registry mapping tables to domains, owning teams, CI numbers, or SLA tiers.

⏱️

Heterogeneous Table Profiles

Tables range from MBs (weekly refresh) to TBs (hourly CDC). A flat policy cannot serve this diversity.

🗑️

Non-Prod Data Sprawl

No lifecycle controls in dev/test environments. Tables created for sprints and load tests accumulate indefinitely. No registry, no creation tracking, no automated cleanup — silent storage cost growth.

🚨

Business Impact at Scale: With 30,000+ tables (a significant subset Iceberg), the platform accumulates millions of orphan files and tens of thousands of snapshots. This causes degraded query performance, inflated S3 costs (potentially $100K+/month from excessive API calls), unpredictable batch times threatening SLAs, and an ever-growing operational risk. The cost and risk grow non-linearly with every passing month.

SECTION 02

Solution Overview

The proposed solution introduces a centralized, registry-driven housekeeping framework designed to govern the Iceberg subset of 30,000+ tables. The framework uses a Python orchestrator on EC2 for decision-making and Athena SQL for execution, with all metadata stored as queryable Iceberg tables.

📋

Registry-Driven at Scale

Every table registered with stream, domain, tier, and dependency info. The registry is itself an Iceberg table — queryable via Athena.

🧠

Health-Driven, Not Schedule-Only

Pre-flight health checks via $files/$snapshots metadata tables. Only run HK when a table actually needs it — cutting unnecessary Athena costs by 50%+.

📡

Observable & Auditable

Execution logs written as Parquet to S3, registered into Iceberg via add_files. Fleet dashboards + per-table drill-down.

♻️

Non-Prod Lifecycle Management

Auto-discovery of unregistered non-prod tables via weekly Glue catalog scan. Greenzone notification workflow with domain owner alerts, objection window, and no-backup cleanup including orphaned S3 metadata and data folders.

Key Architectural Decisions

DecisionChoiceRationale
OrchestratorPython script on EC2 (t3.large / Reserved)No timeout limit. Full boto3 control. Direct Control-M SSH trigger — no container overhead. Multi-threaded / multi-process execution handles 30,000+ table fleet. SSH-accessible for live debugging.
Execution EngineAthena SQL (primary); Glue/EMR (fallback)Athena supports OPTIMIZE + VACUUM natively. No Spark needed. VACUUM has zero compute cost. Glue only for sort/z-order.
Metadata StorageIceberg tables (registry + config)Queryable via SQL. Version history via time-travel. Schema evolution without migrations.
Execution LogS3 Parquet + Iceberg add_filesFast writes (direct S3 put), queryable via Athena after add_files registers into Iceberg table. Avoids slow Athena INSERT.
HK Decision ModelHealth-driven (not schedule-only)Pre-flight queries on $files/$snapshots determine if HK is needed. Skips healthy tables, reducing cost.
ConcurrencyAthena workgroup MaxConcurrentQueriesNative concurrency limit — no custom semaphore needed. Dedicated workgroup isolates HK from production.
Lifecycle OperationsWeekly Lifecycle Engine (same EC2, separate Control-M job)Stale removal and non-prod TTL run on a slower cadence than compaction/vacuum. Separate execution path with independent Athena workgroup and IAM scope — prevents lifecycle ops from interfering with batch-aligned HK.
🐍

Why Python on EC2 over Lambda or ECS Fargate? Lambda's 15-minute timeout forces complex chaining patterns for large fleets. ECS Fargate adds container cold-start overhead (30–90s), ECR image management, and a ~25% cost premium for a workload that is scheduled and predictable — not spiky. A Python script on a Reserved EC2 instance has no timeout, starts immediately, costs ~$30–50/month (vs ~$100–150/month Fargate equivalent), and integrates directly with Control-M via SSH. Multi-shard execution is simply multiple Python processes on the same box. Development parity is perfect — what runs locally runs on EC2 unchanged.

Why Iceberg tables for metadata? All three metadata stores (registry, config, execution log) are Iceberg tables stored in S3. This means: queryable via standard SQL in Athena, version history via time-travel, schema evolution without migrations, and the same HK framework can maintain its own metadata tables. SECTION 05

Why Stream Grouping Matters

🧭

Optional pattern — not adopted. Stream-level grouping (a stream_id tying related tables like finance_staging → finance_master into one logical unit, e.g. STR-FIN-001) is presented below as originally proposed. The organization evaluated this and decided not to adopt the pipeline-stream-grouping model — stream_id and everything derived from it (the CLI --stream-id scope, stream-level Control-M triggering, stream-keyed cost tags) was removed from the schema, CLI, and every code path in the delivered implementation. Treat this section, the stream_id column in Section 06, and any stream_id/STR-FIN-001 references elsewhere in this document as an optional design pattern that may or may not be reconsidered later — not a delivered feature. The Stream Registry table itself (per-table registration — domain, tier, dependencies, etc.) was retained; only the stream-grouping column and concept were dropped.

A stream is the logical grouping of related tables that move data through the layers together as a single business data flow. For example, the "Finance" stream includes finance_staging (staging), finance_datalake (datalake), finance_base (base), and finance_master (master). Stream grouping is the foundation that makes targeted, safe, and scalable housekeeping possible.

Without Stream Grouping (Current State)

❌

30,000+ Tables — No Iceberg Inventory

No way to know which tables are related, which upstream job feeds them, or which batch cycle they belong to. Additionally, not all 30,000+ tables are Iceberg — a discovery phase is required to identify and filter.

❌

No Safe Window Knowledge

Cannot determine when a table is safe to compact — no link between the table and the job that writes to it.

❌

No Dependency Tree

If staging HK fails, there's no way to know which downstream datalake/base/master tables are affected.

With Stream Grouping (Proposed)

✅

Batch-Aligned HK

Trigger HK for an entire stream after its batch completes. All layers maintained together in the correct order.

✅

Dependency Tracking

dependent_on_controlm_job field links each table to its upstream data job. Builds the full dependency tree programmatically.

✅

End-to-End Traceability

Trace issues from master back to staging. Identify which stream a problem table belongs to. Escalate to the right team.

Query Examples

Since the registry is an Iceberg table, any query pattern works directly via Athena SQL:

-- All tables in a stream
SELECT * FROM hk_catalog.admin.stream_registry
WHERE stream_id = 'STR-FIN-001' AND hk_enabled = true;

-- All critical tables in the finance domain
SELECT * FROM hk_catalog.admin.stream_registry
WHERE domain = 'claims' AND tier = 'critical';

-- Build the dependency tree for a stream
SELECT table_fqn, layer, controlm_job_name, dependent_on_controlm_job
FROM hk_catalog.admin.stream_registry
WHERE stream_id = 'STR-FIN-001'
ORDER BY CASE layer
  WHEN 'staging' THEN 1 WHEN 'datalake' THEN 2
  WHEN 'base' THEN 3 WHEN 'master' THEN 4 END;

Last 7 Days Execution Summary — by Domain

-- Tables processed in the last 7 days with outcome breakdown
SELECT
    r.domain,
    r.layer,
    COUNT(*)                                                            AS total_runs,
    SUM(CASE WHEN l.status   = 'SUCCESS' THEN 1 ELSE 0 END)          AS success,
    SUM(CASE WHEN l.status   = 'FAILURE' THEN 1 ELSE 0 END)          AS failed,
    SUM(CASE WHEN l.decision LIKE 'SKIP%'  THEN 1 ELSE 0 END)          AS skipped,
    ROUND(SUM(l.storage_reclaimed_gb), 2)                              AS storage_reclaimed_gb,
    ROUND(AVG(l.duration_seconds) / 60, 1)                            AS avg_duration_mins
FROM      hk_catalog.admin.hk_execution_log  l
JOIN      hk_catalog.admin.stream_registry   r
    ON    l.table_fqn = r.table_fqn
WHERE     l.run_date >= CURRENT_DATE - INTERVAL '7' DAY
GROUP BY  r.domain, r.layer
ORDER BY  r.domain,
          CASE r.layer
            WHEN 'staging'  THEN 1
            WHEN 'datalake' THEN 2
            WHEN 'base'     THEN 3
            WHEN 'master'   THEN 4
          END;

Structured Window Configuration

The window_config JSON block defines when the HK engine is permitted to run for a given table. It is human-readable, version-controlled in the HK Config Iceberg table, and supports IANA timezone names — ensuring correct local-time execution across DST changes. Example:

{
  "type": "scheduled",                // or "post_batch"
  "timezone": "Europe/London",
  "days": ["saturday", "sunday"],      // for scheduled type
  "start_time": "10:00",               // 24h format
  "duration_hours": 4,
  "blackout_hours": [8, 9, 17, 18],    // optional: never run during these hours (UTC or local?)
  "delay_minutes": 30                   // for post_batch: wait after batch completion
}

The orchestrator interprets this configuration using timezone‑aware datetime libraries, ensuring HK runs at the correct local time even across DST changes.

SECTION 08

Python Orchestrator (EC2) — Logic & Intelligence

The orchestrator is a Python script running on a dedicated EC2 instance, triggered directly by Control-M via SSH or by EventBridge via SSM Run Command. No timeout limits — it can process thousands of tables per shard — multi-process/multi-threaded EC2 execution handles the 30,000+ table fleet using boto3 and concurrent.futures for parallelism. It supports multi-scope invocation, idempotency, dynamic partition filtering, and tier-based concurrency control.

The EC2 instance runs two distinct execution modes: the HK Engine (triggered per batch stream by Control-M, handles compaction/vacuum/orphan cleanup) and the Lifecycle Engine (triggered weekly by a separate Control-M job, handles stale table detection and non-prod data retention). Both engines share the same EC2 instance, Iceberg registry, and execution log. Each runs as an independent Python process invoked by its own Control-M job.

Decision Flow (8 phases — health-driven)

PHASE 1 — Discovery
Query Registry + Config via Athena
SELECT r.*, c.* FROM stream_registry r JOIN hk_config c ON r.table_fqn = c.table_fqn WHERE scope_filter AND hk_enabled = true ORDER BY tier, priority
PHASE 2 — Window Evaluation
Schedule Check + Catch-Up Detection
Evaluate window_config (structured JSON) and run_frequency vs. current time and last execution. Uses timezone-aware datetime. Partition into: EXECUTE, CATCH_UP, SKIP.
PHASE 3 — Idempotency Check
Execution Log Deduplication
Generate a unique execution ID (e.g., f"{table_fqn}_{int(time.time())}_{uuid4().hex}"). Check execution log for existing entry with same ID and status 'running' or 'completed'. If found, skip to avoid duplicate dispatch.
PHASE 4 — Property Sync
Ensure VACUUM Properties Are Set
If properties_synced is false, run ALTER TABLE SET TBLPROPERTIES for vacuum settings (snapshot age, min snapshots). Mark as synced in registry after success.
PHASE 5 — Health Check
Pre-Flight via $files and $snapshots
Query each table's metadata: small file count from $files, snapshot count from $snapshots. Skip healthy tables that don't need maintenance — saves 50%+ Athena cost.
PHASE 6 — Dynamic Partition Filter
Derive WHERE Clause from $partitions
Query $partitions to discover partition columns and most recent partitions. Generate a precise filter (e.g., WHERE (year,month,day) IN (...)) to avoid Athena's 100‑partition limit and compact only fresh data.
PHASE 7 — Route & Dispatch
Athena (binpack) or Glue (sort/z-order)
For Athena: dispatch to the appropriate tier‑based workgroup (critical/standard/low) using start_query_execution(). For Glue: invoke a single parameterized Glue job with JSON payload. Use a ThreadPoolExecutor that tracks active queries (via Athena’s GetQueryExecution) and applies backpressure to stay within workgroup limits.
PHASE 8 — Log Results
Write Parquet to S3 + add_files
Write execution results as Parquet file to S3 (one per batch run), including the execution ID, status, bytes scanned, etc. Register into Iceberg execution log via Spark/Athena add_files procedure.

Concurrency Management

The orchestrator uses multiple Athena workgroups (e.g., iceberg-housekeeping-critical, iceberg-housekeeping-standard, iceberg-housekeeping-low) each with its own MaxConcurrentQueries limit. A central ThreadPoolExecutor dispatches queries, but before submitting, it checks the current number of running queries in that workgroup (via list_query_executions and filters by status). If at the limit, it queues the request and retries later with exponential backoff. This prevents throttling and ensures fair sharing.

SECTION 09

Trigger Flow — Detailed Walkthrough

This section explains exactly what happens at each step of both trigger paths — from the moment a batch job completes (or an EventBridge rule fires) through to the execution log write. The flow diagrams in Section 04 show the shape; this section explains the mechanics.

Option A — Control-M Primary: Step-by-Step

Step 1 — Batch Job Completes & Tail Dependency Fires

When a data processing job (e.g. JOB-FIN-BASE) finishes in Control-M, its tail-dependent HK job is released automatically. The HK job is configured with on_failure = alert_only — a housekeeping failure never blocks the next batch cycle. One HK job is defined per stream (or per domain for large deployments), not per table, keeping the Control-M job count manageable across the full fleet.

Step 2 — EC2 Orchestrator Invocation

The Control-M HK job triggers the orchestrator via SSH to the dedicated EC2 instance, passing scope parameters as command-line arguments. No container pull, no task launch delay — the Python process starts in milliseconds. For EventBridge (Option B), invocation uses AWS Systems Manager (SSM) Run Command to execute the script on the EC2 instance without requiring an open SSH port.

# Control-M SSH invocation — arguments scope the run
python3 /opt/zamboni/orchestrator.py   --scope     stream   --stream-id STR-FIN-001   --layer     base   --dry-run   false   --force-run false

# Multi-shard: launch parallel processes for different domains
python3 /opt/zamboni/orchestrator.py --scope domain --domain finance &
python3 /opt/zamboni/orchestrator.py --scope domain --domain finance &
wait  # Control-M waits for all shards to complete
💡

EC2 instance spec: t3.large (2 vCPU, 8 GB RAM) Reserved 1-year term — ~$40/month. One instance hosts all orchestrator shards as parallel Python processes. IAM instance role grants athena:StartQueryExecution, glue:StartJobRun, s3:GetObject/PutObject, and Iceberg catalog access. No ECR, no Docker, no task definitions required.

Step 3 — Phase 1: Registry Discovery

The orchestrator opens by querying the Stream Registry and HK Config tables via Athena using boto3.client('athena').start_query_execution(). It joins both tables on table_fqn, filters to hk_enabled = true and the scope from the payload, then orders by tier (critical first) and priority. The full result is loaded into memory as a prioritised list of table config objects before any processing begins.

Step 4 — Phase 2: Window Evaluation (per table)

For each table in the list, the orchestrator evaluates window_config, run_frequency, and last_execution_time (from the Iceberg execution log). The outcome is one of five states:

DecisionConditionAction
EXECUTE_NOWInside valid window AND run_frequency elapsedProceed to Phase 3
EXECUTE_CATCH_UPMissed a window since last run, allow_catch_up=trueProceed to Phase 3
SKIP_NOT_DUEInside a window but run_frequency not yet elapsedLog & skip — no Athena cost
SKIP_OUTSIDE_WINDOWNot within any valid window_config schedule slotLog & skip — no Athena cost
EXECUTE_FORCEDforce_run=true in payloadBypass all window/frequency checks

Step 5 — Phase 3: Pre-Flight Health Check

Before dispatching any Athena job, the orchestrator runs two lightweight Athena queries against Iceberg's built-in metadata tables. If small_file_count is below compaction_min_files_threshold AND snapshot_count is below the configured maximum, the table is marked SKIP_HEALTHY and logged. No OPTIMIZE or VACUUM is dispatched. This health-driven approach eliminates redundant compaction runs — typically cutting Athena dispatch cost by 50%+ across the fleet, since many tables are already well-maintained from prior runs.

Step 6 — Phase 4: Auto-Partition Filter Generation

Athena enforces a 100-partition limit per OPTIMIZE query. For large partitioned tables, the orchestrator auto-generates a rolling WHERE clause based on the table's processing_cadence: 7-day window for hourly tables, 90-day window for daily tables, 180-day window for weekly tables. Monthly tables get no filter (few partitions, no limit concern). This filter is embedded directly into the SQL string before dispatch. Older partitions were compacted in prior runs — there is no value re-processing them.

Step 7 — Phase 5: Route & Dispatch via ThreadPoolExecutor

Tables cleared by all checks are dispatched in parallel using Python's concurrent.futures.ThreadPoolExecutor. Each worker thread calls boto3.client('athena').start_query_execution() targeting the dedicated iceberg-housekeeping Athena workgroup. The workgroup's MaxConcurrentQueries acts as a native throttle — threads that exceed the concurrency ceiling back off and retry with exponential jitter. Tables with engine = glue_sort or engine = glue_zorder are routed to Glue/EMR Serverless instead via boto3.client('glue').start_job_run(). VACUUM table properties (vacuum_max_snapshot_age_seconds, vacuum_min_snapshots_to_keep) are pre-set during registration — the orchestrator does not ALTER them at runtime.

Step 8 — Phase 6: Execution Log Write

After all dispatched queries complete (or reach max_execution_minutes timeout), the orchestrator writes a single Parquet file to S3 — one record per table evaluated in this run. Key fields include decision, status (SUCCESS / FAILURE / TIMEOUT), duration_seconds, files_before, files_after, and storage_reclaimed_gb. The file is then registered into the Iceberg execution log table using PyIceberg's add_files() — a direct S3 manifest update that makes the new records immediately queryable in Athena without a slow INSERT.

📅

EventBridge Safety Net (Option A only): An EventBridge rule fires every 6 hours with scope=all and force_run=false. The orchestrator evaluates every registered table, but Phase 2 handles deduplication — any table already processed within its run_frequency window gets SKIP_NOT_DUE. Only tables whose Control-M HK job was missed, failed, or skipped actually dispatch Athena queries. The safety net adds negligible cost because the window check and skip path is cheap (no Athena involved).

Fleet-Wide Scope and Concurrency

Unlike Option A which scopes to a specific stream, Option B processes the entire registered fleet on every invocation. In practice the vast majority of tables are eliminated early — by Gate 1 (upstream not done), G2 (outside safe window), or G3 (table is healthy) — so the actual Athena dispatch count stays well within workgroup concurrency limits. Tables are processed in tier-priority order, ensuring critical streams are evaluated and dispatched before standard or low-priority ones even if the run is time-constrained.

⚠️

Circuit Breaker — both options: If any table accumulates 3 consecutive FAILURE entries in the execution log, the orchestrator automatically sets hk_enabled = false in the Stream Registry via an Iceberg MERGE and fires an SNS email alert to the owning team. The table is excluded from all future runs until manually re-enabled after investigation. Note: Microsoft Teams supports incoming webhooks — if the organisation uses Teams, alerts can be forwarded from SNS via a Lambda-to-webhook bridge, but this is not part of Zamboni's scope and would be a separate integration. This prevents a persistently failing table from consuming Athena quota on every HK cycle.

Athena (built on Trino) natively supports Iceberg maintenance operations. The Python orchestrator executes these as SQL queries via boto3. Several refinements have been added to address edge cases.

VACUUM Combined Operation – Important Note

Athena’s VACUUM combines snapshot expiry and orphan cleanup using a single retention setting (vacuum_max_snapshot_age_seconds). This may not suit tables that require different schedules (e.g., expire snapshots daily but keep orphans for a week). For such cases, the policy template’s engine field should be set to glue, and the orchestrator will route the table to the parameterized Glue job, where expire_snapshots and remove_orphan_files can be called independently.

Pre‑VACUUM Safety – Iceberg Tags

Instead of relying on S3 versioning, the orchestrator can create an Iceberg tag before running VACUUM (if create_backup_tag is true). A tag is a named reference to a specific snapshot and costs nothing. In case of accidental data loss, you can query the table as of that tag or even roll forward. Example:

-- Create a tag before VACUUM
ALTER TABLE db.iceberg_framework_test CREATE TAG 'pre_vacuum_20260321_1030';

-- Run VACUUM
VACUUM db.iceberg_framework_test;

-- If recovery needed:
SELECT * FROM db.iceberg_framework_test VERSION AS OF 'pre_vacuum_20260321_1030';

Dynamic Partition Filter (Phase 6)

Instead of a heuristic rolling date filter, the orchestrator queries $partitions to build a precise filter. This works for any partition scheme and avoids the Athena 100‑partition limit. Example:

-- Get the 100 most recent partition tuples
SELECT partition FROM "db.table$partitions"
ORDER BY partition DESC LIMIT 100;

-- Then construct a WHERE clause like:
WHERE (year, month, day) IN (('2026','03','20'), ('2026','03','21'), ...)

Athena Table Properties for VACUUM Control

VACUUM retention is controlled via table properties — set once during registration (Phase 4). The orchestrator tracks properties_synced in the registry to avoid repeated ALTERs.

Cost Attribution via Query Tags

When starting an Athena query, the orchestrator includes tags in the StartQueryExecution call: hk-table-fqn, hk-domain, hk-tier. These tags appear in AWS Cost and Usage Reports, enabling per‑table/domain cost analysis.

2) Adaptive Throttling + Quota Isolation

  • Isolate workgroups by tier so low-tier HK never blocks business-critical workloads.
  • Adaptive throttling reduces dispatch when median Athena duration rises or failure rate spikes.
  • Token bucket per shard (e.g., critical=20, standard=10, low=5) with dynamic adjustment.

3) Partition-Introspection Filtering

  • Build OPTIMIZE filters using the table's actual partition spec from Iceberg metadata.
  • Maintain a safe fallback: if partition cannot be inferred, restrict to a bounded time window using the most recent partition values.
  • Record the exact filter used in execution logs for audit and troubleshooting.

4) Circuit Breakers + Auto-Quarantine

  • Per-table breaker: after N consecutive failures, set lifecycle_state=QUARANTINED.
  • Fleet breaker: if failure rate exceeds threshold (e.g., 30% of dispatched ops), stop dispatching and alert.
  • Degraded mode: VACUUM-only (or health-check-only) when Athena is unstable.

5) Resumable Runs via Checkpoints

Each orchestrator shard writes a lightweight checkpoint record per table-operation pair (table_fqn, operation, run_id, status, attempt, started_at, ended_at). On restart, the shard resumes from the last incomplete checkpoint instead of re-scanning everything.

6) Explicit Self-Housekeeping

The HK framework's own Iceberg tables (registry/config/log/checkpoints) are onboarded as a protected stream with conservative retention and strict guardrails (no aggressive VACUUM, controlled OPTIMIZE cadence).

7) Pre-VACUUM Recovery Anchor (Iceberg Tag/Branch)

10) Partition Filter from Iceberg Metadata

The cadence-based WHERE clause heuristic is fragile at scale. Derive partition filters from the table's actual partition spec via Iceberg metadata (preferred), and fall back to heuristics only if metadata access fails. This prevents costly full-table OPTIMIZE runs and avoids the 100-partition limit.

  • Fallback: registry-stored structured spec (not a free-text string), validated against metadata periodically.

11) VACUUM Properties Pre-Flight Sync

VACUUM retention is controlled via table properties. The framework must guarantee those properties are set before first execution. 12) Athena Concurrency Contention — Mitigation

Athena concurrency is a shared, hard throttle per workgroup. Under load, contention causes queueing, throttling errors, and longer runtimes that can push HK outside safe windows. Mitigation: tier-aware dispatcher with dedicated workgroups per tier and adaptive throttling.

13) Idempotency

Introduce a strict idempotency key per operation (e.g., run_id + table_fqn + operation + window_id). Store it in the execution log and pass it as the client token where supported. Retries must become "resume" (no duplicate dispatch) rather than "re-run."

New registrations start in DRY_RUN mode (default 7 days): the orchestrator runs discovery + health checks, produces the exact SQL it would execute, estimates partitions touched, and logs recommendations — but performs no OPTIMIZE/VACUUM. 15) Cost Attribution

Stamp a consistent query_tag on every Athena/Glue execution with dimensions domain, stream_id, and tier. Generate a monthly report from execution logs: runtime, bytes scanned, success rate, and estimated cost per domain.

⛔

🔐

Trigger: A deployment removes required permissions for Athena/Glue/S3.

FS-03: Orchestrator Task Crash Mid-Run

💥

Trigger: EC2 process killed (OOM, OS-level interruption, instance stop).

Framework behavior: Checkpoints ensure idempotent resume. Next trigger restarts shard and continues from last incomplete table-operation pair.

Outcome: Partial progress preserved; no double-work beyond safe retries.

FS-04: Table-Level Lock/Conflict with Active Writes

🧱

Trigger: HK overlaps with a late-running batch write; Athena OPTIMIZE conflicts.

Framework behavior: The safe-window gate prevents most collisions. If a conflict occurs, the table breaker retries with exponential backoff; after N failures it auto-quarantines.

Outcome: One table is isolated; the fleet proceeds.

FS-05: Registry Drift (Partition spec or table properties changed)

🧭

Trigger: Partition evolution or property change not reflected in registry/config.

Framework behavior: Drift Scanner detects mismatch, updates a drift table, and sets affected tables to MIGRATING (restrict operations to safe subset).

Outcome: Prevents accidental full scans and incorrect partition filtering.

FS-06: Execution Log Table Becomes a Hotspot

🧾

Trigger: High-frequency runs create many small log files; log table snapshots grow quickly.

Framework behavior: The HK framework schedules self-housekeeping for log tables (weekly compaction + conservative retention).

Outcome: Observability remains cheap and fast; metadata growth stays bounded.

The Lifecycle Engine addresses the second major gap in the platform: non-production data sprawl. STEP 3 — Export to Archive
Write Parquet to archive S3 with Intelligent-Tiering
Write via awswrangler.s3.to_parquet() with s3_additional_kwargs={"StorageClass": "INTELLIGENT_TIERING"}. Destination: s3://prod-staging-archive/staging_archive/<domain>/partition_date=<date>/. Compression: Snappy. Max rows per file: 10M. Partition-level parallelism via ThreadPoolExecutor.
STEP 4 — Post-Archive Validation
Verify archive completeness before delete
Checks: ✓ files exist in archive prefix (list_objects_v2) · ✓ row count query on archive matches source (±0.1%) · ✓ file sizes reasonable. If any check fails: ABORT — do not delete from staging. Log critical error, send SNS alert. Partition stays in staging until next run.
STEP 5 — Delete from Staging
Remove partition from live Iceberg staging table
Execute via Athena: DELETE FROM <staging_table> WHERE partition_date = '<date>'. This creates a new Iceberg snapshot marking partition files as deleted. Snapshot expiry is handled separately by the HK Engine on its own schedule — the Archival Engine does not call expire_snapshots.
STEP 6 — Log & Metrics
Write execution log entry, publish CloudWatch metrics
Write to hk_catalog.admin.hk_execution_log with operation = 'archival': partition date, rows archived, GB reclaimed, archive S3 path, validation outcomes, duration. Publish to CloudWatch: PartitionsArchived++, RowsArchived += row_count, DataArchivedGB += size_gb. Send weekly summary via SNS.
🔒

Delete is conditional on post-archive validation passing. The Athena DELETE only executes if the archive S3 files exist and the row count reconciles within 0.1%. A failed post-archive check leaves the partition intact in staging and raises a critical SNS alert — the partition will be retried on the next weekly run.
